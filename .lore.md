## Long-term Knowledge

### Architecture

<!-- lore:01a043d7-502d-7de9-9416-66f3050c12b7 -->
* **approval-authorizer GitHub roles**: Chose live target-repository collaborator permissions over private \`security-as-code\` because GitHub reflects effective access without exposing internal RBAC. Humans authorize only with \`write\`, \`maintain\`, or \`admin\`; \`triage\` never authorizes. \`getsantry\[bot]\` and \`sentry-release-bot\[bot]\` may authorize only through the explicit allowlisted, attested automation path, while \`sentry-internal-app\[bot]\` and every other \`\[bot]\` identity are rejected by normal collaborator authorization. Bot repository access alone does not prove approved automation provenance.

<!-- lore:01a082db-d8b9-7438-927a-07bf7aa5e369 -->
* **production environment secret boundary**: Chose the protected \`production\` environment over repository- or organization-scoped publishing secrets because its \`main\`-only policy and disabled admin bypass gate credential access. Exceptions: \`SENTRY\_INTERNAL\_APP\_PRIVATE\_KEY\` and \`SENTRY\_RELEASE\_BOT\_PRIVATE\_KEY\` are organization-wide and this repository cannot isolate them; workflow guards cannot narrow that exposure. Treat it as a separate Security-led risk and block only if the current change worsens it.

<!-- lore:01a0df6d-68b4-74ad-82aa-fd81459c5ff5 -->
* **PUBLISH\_ATTESTATION\_SECRET retry-shell isolation**: Use \`PUBLISH\_ATTESTATION\_SECRET\` only for HMAC approval, auto-approval, and ci-ready attestations. Trap: exposing it across a retry shell looks convenient because retries share environment state, but it leaks the credential to \`sleep\`, GitHub API commands, checkout, token actions, and target-revision Craft code. Fix: inject it only into inline Node attestation commands, with no step- or shell-wide secret environment.

<!-- lore:01a0df6d-691e-7458-b748-ff48191acbbe -->
* **publish-and-validate canonical path fence**: Keep \`src/publish/publish-and-validate.js\` as the final in-container fence: validate the live request, exact revision, unique release branch, branch head, and canonical publish-path containment immediately before Craft. Lexical \`path.resolve\`/\`path.relative\` checks look sufficient but accept symlinks that escape \`\_\_repo\_\_\`; canonicalize the relevant paths and reject escapes before spawning Craft.

<!-- lore:01a082d6-7a23-7094-9eda-65dbdf093998 -->
* **publish.yml Craft state isolation**: Chose \`$GITHUB\_WORKSPACE/.craft-state\` with explicit \`XDG\_STATE\_HOME\` over state inside the target checkout because untrusted repository contents could pre-populate privileged Craft state. Derive collision-resistant state filenames from canonical publish identity, and set \`CRAFT\_PUBLISH\_STATE\_GITHUB\_REPO\` from the issue checkout repository—not an optional workspace release-repository override—so restoration and publication use the same identity.

<!-- lore:01a0e0d2-37df-7259-bba2-a1f516cc7cd5 -->
* **publish.yml packages write scope**: Chose job-scoped \`packages: write\` for the publishing job over workflow-wide permissions because \`waiting-for-ci\` only observes release state and must not inherit registry write capability. Workflow-wide permissions look simpler and preserve shared defaults, but they enlarge the privilege boundary for a non-publishing job. Keep permission separation covered by workflow regression tests.

### Gotcha

<!-- lore:01a04dbc-a980-7623-8218-a792b8a6c8c2 -->
* **approval attestation request digest**: Trap: validating an attestation against current live state looks sufficient, but the workflow may consume older event payload inputs after the issue changes. Fix: SHA-256 hash exact \`{title, body, dryRun}\` event state, require \`EXPECTED\_REQUEST\_DIGEST\` at every executable and exported validation boundary, and compare it with live state before minting or consuming proofs. Exclude transient workflow labels; any title, body, or \`dry-run\` change requires renewed approval.

<!-- lore:01a044d9-1f72-7d7c-947d-b7359eadc0f9 -->
* **approval-attestation unsafe event IDs**: Trap: converting GitHub issue-event IDs to JavaScript numbers before string comparison looks harmless because API payloads serialize IDs as strings and numeric comparison is convenient, but IDs above Number.MAX\_SAFE\_INTEGER can round and make stale/current-event checks compare the wrong event. Fix: preserve IDs as decimal strings, validate their canonical decimal form, and fail closed on unsafe numeric inputs; do not use BigInt because this repository’s ESLint environment rejects it.

<!-- lore:01a043d7-509e-7386-8020-84bfd729b791 -->
* **approval-authorizer legacy titles**: Trap: retaining \`PUBLISH\_TITLE\_REGEX\` beside the generated parser looks useful for authorization compatibility, but creates parser drift between approval, CI, and publication. Fix: use generated \`parsePublishIssueTitle()\` plus shared validators everywhere; \`parsePublishTitle()\` remains non-throwing and returns \`null\` for authorization failures. Edit \`src/modules/publish-issue-title.peggy\` and regenerate—never hand-edit or merge \`publish-issue-title.js\`.

<!-- lore:01a082a6-e344-787f-bd73-8d7c9d276f62 -->
* **approval-authorizer unused autoApprovedRepositories**: Trap: retaining \`autoApprovedRepositories\` in \`authorizeApproval()\` looks harmless after direct bot authorization is removed, because it was previously part of the automated-approval path. It becomes an unused parameter and fails this repository’s ESLint \`no-unused-vars\` check. Fix: remove the argument when the Internal App attestation path no longer needs it; do not suppress the lint rule.

<!-- lore:01a0895a-0b77-7f43-8c39-ef79439fb803 -->
* **authorization fixture open-state**: Trap: mutation or self-approval fixtures without \`state: "open"\` look adequate because the intended invalid condition is present, but entry points reject the issue at the earlier open-state guard. Fix: establish every prior precondition—including open state—so removing the self-approval, title-mutation, or accepted-event guard makes the regression fail.

<!-- lore:01a0ceb7-d896-73a4-b2ef-117f2046db81 -->
* **authorize-approval auto-approve-repos path**: Trap: reading \`auto-approve-repos.txt\` with a process-relative path looks correct from the repository root, but the publish job executes checked-out code under \`.\_\_publish\_\_\`, so the policy file may be missing and automated authorization fails or behaves inconsistently. Fix: resolve the allowlist from the trusted checkout/module location, and test authorization from the actual publish working directory rather than only from the repository root.

<!-- lore:01a082a0-f4d7-7964-af6c-337d3d7f4374 -->
* **authorize-approval.js AUTO\_APPROVERS direct-label bypass**: Trap: allowing \`getsantry\[bot]\` or \`sentry-release-bot\[bot]\` through generic \`AUTO\_APPROVERS\` authorization looks safe because both are approved automated requesters, but either could directly add \`accepted\` to the other’s request and bypass the Internal App’s request-bound proof. Fix: \`authorizeApproval()\` must fail closed for direct labels by both bots; only \`sentry-internal-app\[bot]\` may represent automated approval, backed by the matching \`github-actions\[bot]\` attestation. Cover both direct-bot paths with regressions.

<!-- lore:01a0dfd2-0900-7220-865c-8291bdbeed4d -->
* **auto-approve accepted-label stranding**: Trap: adding \`accepted\` before recording the automated attestation looks necessary because proof should bind to the live label event, but label success followed by command or output failure can strand authorization before normal cleanup or poller activation. Fix: establish an independent recovery marker/path before the label mutation, and make post-label attestation, output, poller, and dispatch failures revoke \`accepted\` without requiring \`approved=true\`; scheduled reconciliation remains the final recovery path.

<!-- lore:01a0895a-0b31-7cad-9c1f-9ac3b8c96b81 -->
* **auto-approve sparse checkout**: Trap: sparse-checking out only \`auto-approve-repos.txt\` looks sufficient because it is the workflow’s policy input, but \`auto-approve.yml\` also runs \`src/publish/record-auto-approval-attestation.js\`; the absent script fails with \`MODULE\_NOT\_FOUND\`. Fix: include the entry point and its local dependencies in sparse checkout, and test checkout contents—not only textual step ordering.

<!-- lore:01a043ee-6e48-7a54-8fcc-113e286f32a1 -->
* **auto-approve.yml accepted-event binding**: Automated approval must bind the attestation to the exact current \`accepted\` label event, not merely the Internal App actor, title, and request digest. A newer acceptance by the same bot can otherwise reuse an older proof. Record and validate \`acceptedActor\` and \`acceptedEventId\`, require the allowlisted repository and trusted \`github-actions\[bot]\` proof, and revoke \`accepted\` on malformed input or any snapshot change.

<!-- lore:01a0ce7c-78f7-7a2b-be62-1ba7a3a00bc2 -->
* **ci-poller accepted-only pending scan**: Trap: relying on \`CI\_POLLER\_HAS\_PENDING\` or scanning only issues with a complete \`ci-pending\` plus \`accepted\` combination looks efficient, but failed cleanup and stale variables can strand \`accepted\`, \`ci-ready\`, or \`ci-pending\`. Fix: scheduled poller runs must always scan open non-PR issues carrying any authorization label (\`accepted\`, \`ci-pending\`, or \`ci-ready\`), reconcile stale state, and keep recovery enabled even when authorization-listing or cleanup steps fail.

<!-- lore:01a08c39-2536-765c-8462-dd60705cef99 -->
* **ci-poller branch-head reread**: Trap: checking the release branch head once looks sufficient because CI was evaluated against that SHA, but the branch can move before promotion. Fix: read the authoritative branch head again immediately before adding \`ci-ready\`; if it differs from the checked revision, rewrite the issue with the new revision, revoke approval/pending state, and stop. Never promote the SHA that was checked after the branch moves.

<!-- lore:01a0898d-7954-7683-a4f5-a2b1875a0cf5 -->
* **ci-poller cross-command ordering**: Trap: comparing separate \`gh\` and \`node\` logs looks sufficient because each records the expected calls, but their indices cannot prove cross-command order. Fix: append both stubs to one event log and assert stale \`ci-ready\` removal occurs before final approval validation, which occurs before adding fresh \`ci-ready\`.

<!-- lore:01a04dbc-aa3b-71ad-aa12-02cf42d9cb54 -->
* **ci-poller deauthorization recovery**: Trap: leaving \`Mark ci-pending\` unguarded or swallowing final deauthorization failures looks fail-closed because the current job stops, but it can strand \`accepted\` without \`ci-pending\`, while the poller scans only recoverable label combinations. Fix: restore or retain recoverable state when pending-marking fails, and if \`ci-ready\` promotion plus pending restoration fails, retry or surface independent removal of \`accepted\`; recovery must not depend on a later labeled event.

<!-- lore:01a0e0ba-0c8f-7e1e-af9d-76aaf472a5a6 -->
* **ci-poller immutable default-branch checkout**: Trap: validating the default branch and then checking out its mutable name looks safe because both initially resolve to the same revision, but the branch can move before checkout and load changed privileged workflow code. Fix: checkout the immutable validated run SHA or trusted handoff commit, never \`github.event.repository.default\_branch\`; add a regression proving the branch-move race cannot reach secret-bearing poller logic.

<!-- lore:01a0dfd2-09cc-7c31-9846-b56d0c4c4d50 -->
* **ci-poller requires complete CI evidence**: Trap: treating one successful commit status as complete CI looks reasonable because GitHub exposes a green combined status, but it can represent an arbitrary context while required checks are absent or check runs are incomplete. Fix: bind readiness to the authoritative required checks or branch-protection result, require complete expected evidence for the exact revision and release branch, and reject missing, partial, ambiguous, or zero-check results; retain a regression for one successful status with no check runs.

<!-- lore:01a08b5e-d1ae-7fe4-b73f-6a5b02fbc76e -->
* **ci-poller subshell continue**: Trap: \`continue\` in \`.github/workflows/ci-poller.yml\` rejection branches looks right because issue processing resembles a loop, but each issue runs inside a piped-loop subshell where that \`continue\` is invalid and execution can still add \`ci-ready\`. Fix: use \`exit 0\` to terminate the rejected issue’s subshell; mutation tests must prove replacing it with \`continue\` advances stale state.

<!-- lore:01a082db-d8f8-718f-837b-a2f3b4c3ddbb -->
* **ci-poller-dispatch repository secrets**: Trap: \`permissions: {}\` on \`.github/workflows/ci-poller-dispatch.yml\` looks sufficient because it removes \`GITHUB\_TOKEN\`, but repository secrets remain injectable into caller-selected workflow YAML. Fix: the relay must never use repository secrets; use only \`production\` environment secrets after migrating values there, with the environment restricted to \`main\`. This preserves required \`workflow\_dispatch\` recovery without letting an arbitrary ref expose privileged credentials.

<!-- lore:01a04d92-ba58-78f6-ac20-11235bea2ee6 -->
* **ci-poller.yml attestation output sourcing**: Trap: \`source "$attestation\_output"\` looks convenient because GitHub output files use \`key=value\` lines, but it executes the attestation payload as shell code. Fix: read the known \`ci\_ready\_attestation\` value as literal data and validate its expected format; the proof is untrusted transport data until the validator checks its trusted comment author, title, event, and actor bindings.

<!-- lore:01a049f3-5509-754e-b025-4c98ee6b8247 -->
* **ci-ready attestation provenance**: Trap: snapshotting the \`accepted\` event after initial validation looks equivalent because validation checks the live label, but a rename or re-approval can occur in that gap and become the event CI binds. Fix: snapshot the current accepted actor/event before validation, fail closed and clean up labels if the event read fails, and pass that exact binding through both validations and CI-ready attestation recording. Immediately before adding \`ci-ready\`, verify the same title and event again. A renamed or re-approved issue must never reach \`ci-ready\`; the proof and live label actor must also match.

<!-- lore:01a0dfb1-3a55-73dc-a498-c84ed48c1782 -->
* **cocoapods-keepalive immutable checkout**: Trap: pinning \`cocoapods\` and locking Bundler dependencies looks reproducible, but \`.github/workflows/cocoapods-keepalive.yml\` can still check out mutable \`main\` before using \`COCOAPODS\_TRUNK\_TOKEN\`; a branch move can inject unreviewed code. Fix: pin checkout to a reviewed immutable commit, retain \`Gemfile.lock\`, run \`bundle exec pod trunk me\`, and keep the job behind the protected \`production\` environment.

<!-- lore:01a082eb-7127-707f-85a0-633cf5fcf359 -->
* **cocoapods-keepalive.yml yml/plain-scalar**: Trap: quoting the workflow \`name\` in \`.github/workflows/cocoapods-keepalive.yml\` looks harmless because YAML accepts either scalar style, but this repository's ESLint YAML rule requires a plain scalar and fails \`yarn lint\`. Fix: use \`name: CocoaPods Token Keep-Alive\`; run \`eslint src .github --ignore-pattern '!.github'\` after workflow edits because YAML style violations may be outside the changed release workflow.

<!-- lore:01a0e08d-5137-728a-89a6-a05456239f37 -->
* **current-ci-ready-event null bypass**: Trap: returning null when no current ci-ready event exists looks tolerant because the poller can treat it as an empty previous-event ID, but an inconsistent API read then skips stale-event comparison and weakens fresh-event binding. Fix: when fresh-event validation requires a prior event snapshot, distinguish 'no event' from an unreadable or inconsistent event response and fail closed; add a regression covering the null path through record-ci-ready-attestation.

<!-- lore:01a08c39-24ef-7f07-a0f6-a1757e25c2c4 -->
* **currentLabeledEvent latest transition**: Trap: filtering to valid \`labeled\` events before choosing the newest event looks correct because callers want the current label application, but it ignores later \`unlabeled\` transitions and malformed relevant IDs; a singleton malformed ID also bypasses comparator validation. Fix: validate every relevant ID, select the newest \`labeled\` or \`unlabeled\` transition, and return null unless it is a valid \`labeled\` event with an actor.

<!-- lore:01a082ad-90f9-792a-9bbb-ec1cbaed60e6 -->
* **detailsFromContext missing issue guard**: Trap: dereferencing \`parsePublishTitle(title).groups\` looks concise because workflow issue contexts normally include a valid publish title, but manual or unexpected contexts yield an opaque TypeError. Fix: \`detailsFromContext()\` must explicitly reject absent issue context and malformed titles before accessing groups, using actionable errors. Chose explicit validation over implicit dereference because callers need fail-closed, diagnosable rejection of invalid publish requests.

<!-- lore:01a1021a-ae47-758a-bf0d-130b4e01a5a4 -->
* **pnpm-lock.yaml Prettier exclusion**: Trap: running Prettier over every file looks consistent with Sentry Publish’s formatting checks, but it flags pnpm’s generated lockfile. Fix: exclude \`pnpm-lock.yaml\` in \`.prettierignore\` rather than rewriting generated dependency data; continue formatting source and checking the lockfile with a frozen pnpm install.

<!-- lore:01a0df90-411e-7dca-9791-0d37c9fd2ee4 -->
* **processEndState close failure telemetry**: Isolate successful issue closure from terminal reporting and telemetry. Closing the issue first looks orderly, but a transient \`issues.update\` failure can otherwise abort workflow lookup, result comments, and Sentry reporting; treat closure as retryable or nonfatal so the terminal outcome remains observable.

<!-- lore:01a0ceb7-d8f5-7e15-8c31-d634683c8793 -->
* **processEndState telemetry after comment failure**: Trap: awaiting issue-comment publication before telemetry looks orderly because the comment is part of terminal reporting, but a GitHub comment or workflow lookup failure can prevent Sentry telemetry entirely. Fix: isolate optional comment/reporting failures from \`withScope\`, \`captureMessage\`, session completion, and \`Sentry.close()\` so failure and cancellation telemetry still runs; test comment rejection explicitly.

<!-- lore:01a04dbc-a9c0-7728-87ae-189a0d738d77 -->
* **publish Consume approval TOCTOU**: Trap: validating approval immediately before \`Consume approval\` looks safe because the fence checks live labels, title, events, digest, and CI proof, but consuming labels creates a mutable window before Craft starts. Fix: after every label mutation and immediately before Craft, revalidate the live request, accepted-event provenance, CI-ready proof, title, digest, branch revision, and open state; abort and revoke on any change. Earlier validation cannot authorize publication of a changed snapshot.

<!-- lore:01a08c39-25ef-754c-a83c-0a5e23ff1ab8 -->
* **publish Inform start gate**: Trap: leaving \`.github/workflows/publish.yml\`’s \`Inform start\` step unguarded looks reasonable because publication status should be announced, but transient workflow-run lookup or comment failures then block checkout and Craft. Fix: mark this informational step \`continue-on-error: true\`; authorization fences and publication remain mandatory, while comments and telemetry are best-effort.

<!-- lore:01a08b5e-d1f4-7ca9-957d-bbd89f7df58d -->
* **publish reconciliation mutation anchoring**: Trap: globally removing a repeated reconciliation command looks like a valid mutation because both \`.github/workflows/publish.yml\` blocks contain nearly identical label cleanup, but it may mutate the earlier best-effort block instead of the final authoritative block. Fix: anchor mutations to the named \`Verify publish issue reconciliation\` section and inspect the diff before testing so the regression proves the intended final-cleanup invariant.

<!-- lore:01a043d7-5066-73ab-8e45-64a4796ddeb5 -->
* **publish terminal reporting**: Trap: parsing \`PUBLISH\_ARGS\` at module load or using separate \`always()\` steps for cancelled, failure, and success looks straightforward, but missing inputs can suppress reporting and cancellation predicates can overlap. Fix: parse inside \`main()\` with a warning and fallback, then use one \`always()\` reporter that derives exactly one status from the Craft outcome. \`update-issue.js\` uses undefined to skip target restoration; \`post-result.js\` uses \`{}\` so reporting continues.

<!-- lore:01a04dbc-a9ff-7c0d-bcf4-b031f598dfd0 -->
* **publish.yml Craft latest image**: Trap: \`docker://getsentry/craft:latest\` looks convenient, and rewriting the pinned image as \`ghcr.io/getsentry/craft@…\` looks like equivalent registry hardening, but \`latest\` is mutable and the GHCR image is unavailable. Keep a regression that simulates deletion failure.

Fix: set \`package\_json\_file\` to \`.\_\_publish\_\_/package.json\`, point the cache at \`.\_\_publish\_\_/pnpm-lock.yaml\`, and install with \`pnpm --dir .\_\_publish\_\_ install --frozen-lockfile\`. The separate \`waiting-for-ci\` job also needs its own install before running repository Node modules because jobs do not share dependencies.

* **publish.yml release-token scope**: Trap: passing a broad release-bot installation token as GITHUB\_TOKEN and GITHUB\_API\_TOKEN to Craft looks convenient because target lifecycle code may need GitHub access, but it can grant organization-wide write access to approved target-repository code. The publish workflow’s target-repository token is still privileged and must remain behind final live-state validation.

* **publish.yml title snapshot TOCTOU**: Trap: checking the mutable issue title and current \`accepted\` event at each stage looks safe because each check validates live state, but it permits a re-approval during a CI poll to replace the approval that CI actually evaluated. Fix: bind authorization to exact title and accepted-event ID, capture that event before CI work, and pass it as \`expectedAcceptedEvent\` through final validation and CI-ready-proof recording. Fix: bind the requested branch explicitly to the release snapshot and require every poller and publication fence to validate that exact branch; otherwise reject rather than selecting metadata-derived state.

Fix: \`runPoller\` must replace GitHub expression placeholders with test values before execution; otherwise scoped-secret workflow changes produce misleading failures unrelated to poller behavior.

<!-- lore:01a08c39-25ab-7f2c-bcd7-b8d28b589848 -->
* **updateIssue independent cleanup failures**: Trap: awaiting target restoration and \`accepted\` removal with \`Promise.all()\` looks efficient, and treating a missing label as harmless seems sufficient, but one rejection can hide the other operation’s result and non-404 label failures can strand authorization. Preserve the issue for retry after unsuccessful publication.

* **workflow-action-pinning full commit SHAs**: Trap: GitHub Action version tags such as \`actions/checkout@v6\` look maintained and reproducible, but tags are mutable and let secret-bearing workflows execute changed third-party code without review. Chose immutable SHAs over tags because privileged workflows expose Internal App and release tokens.

### Preference

<!-- lore:01a0d935-1f75-784b-8462-a6a76c72a458 -->
* **Always audit publish authorization end to end**: When working on the publish or approval system, trace authorization across the Node.js code, GitHub workflows, issue labels/events, attestations, repository allowlists, and CI gates. Verify exact actor identities, title and digest matching, accepted/ci-ready sequencing, permission roles, protected production-environment secrets, immutable action references, and failure outputs. Treat automated approval provenance and final publication fencing as security-critical, and inspect both implementation and tests/workflows before making changes.

<!-- lore:01a0d9af-721d-798e-88dc-e6ba58fc1cf2 -->
* **Always audit release automation for security and workflow correctness**: When examining release infrastructure, systematically trace the end-to-end workflow: document release inputs and approval rules, inspect GitHub Actions and token/secret usage, verify protected-environment and permission boundaries, check action pinning, and validate all user-controlled repository, path, and version inputs. Confirm security-sensitive behavior with focused tests, including authorization, self-approval prevention, attestation integrity, malformed input rejection, and failure handling. Record exact files, lines, identities, scopes, and API interactions so the implementation and its security assumptions are unambiguous.

<!-- lore:01a082d6-1536-7da7-9a6f-8ec4b1c78ad6 -->
* **Always enable workflow\_dispatch for manual recovery**: Ensure CI polling retains a reliable manual recovery path triggered through \`workflow\_dispatch\`. Do not remove or condition this capability on pending-work variables, cron state, or other automation. When the security design uses a protected relay, keep \`workflow\_dispatch\` on that relay and route privileged execution only through the trusted path; when direct dispatch is explicitly required, retain it on \`ci-poller.yml\`. Treat this recovery mechanism as an enforced workflow invariant and cover it with tests.

<!-- lore:01a0dfb7-9174-75b9-bd11-9b2eb0db7903 -->
* **Always enforce explicit, immutable, independently verified release authorization**: Treat every release as a security-sensitive request: require approval from a second person, keep attestation secrets separate from publishing credentials, and never reuse proof across requests or approval events. Bind authorization to the exact issue title, body, labels, requester, repository/workspace identity, approved revision, and current event IDs. Preserve exact user-supplied workspace paths and identities rather than normalizing them.
